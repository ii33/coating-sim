# 助手讨论模式与持久计算放行合同

更新：2026-10-15。此合同不改变物理算法、数值语义或计算结果格式。

## 来源、状态所有者与输入输出

- UI 中“讨论”沿用内部模式键 `chat`（`/plan` 与兼容 `/chat` 指向同一模式）。讨论只能读取与规划，不能创建新计算、批准、提交或通过旧回执恢复操作。任务小于等于 60 秒也没有例外。
- `AssistantStore` 的 `assistant_ui_session_modes(session, mode, generation, updated)` 是桌面 UI 当前会话模式的唯一持久授权来源；`assistant_ui_requests(session, request_id, mode, generation, created)` 是 UI 在启动实际请求前绑定的不可改写来源。两表按已有会话身份关联，schema 创建幂等；既有聊天、进度日志和请求历史不被迁移为授权。
- `set_ui_session_mode` 由桌面模式选择、配置保存/重载和会话初始化调用。同模式不增代际；实际模式变更增加代际。全局模式选择同步所有保留会话，避免隐藏会话里的旧倒计时继续放行。配置中的模式成功持久化到授权表后才更新 bridge 当前配置。
- `bind_ui_request` 由桌面请求启动路径调用一次，输入是 UI 实际将传给 worker 的运行配置模式，包括 UI 生成的 `config_overrides`。它记录当前会话代际，不能重新标记同一请求。运行模式覆盖不能越过当前会话的讨论限制。后台通知的只读模式同样绑定为讨论。
- 这两个 UI 写方法不在 MCP 或 `project_action` 工具目录中。模型给出的 `mode`、任意工具参数、恢复回执、worker `progress/received` 事件或可见文本都不是授权依据。`received` 仅用于日志。
- `ComputeTaskStore` 负责估算、回执与资源放行；调度器负责真正的队列身份、进度与终态。计算请求只携带真实 `session_id/request_id`，放行服务按二者查询上述 UI 表，不接受调用方自报模式。

## 放行规则与错误

1. 助手请求的绑定模式或当前会话模式为 `chat`，返回 `compute_discussion_read_only`；可信 UI 记录缺失返回 `compute_ui_authority_missing`；请求代际已过期返回 `compute_ui_mode_changed`。
2. 可信、当前代际的 `operate` 保留十秒倒计时；`research` 保留立即放行。没有助手来源的独立外部请求保留显式手动确认。用户直接点击 GUI 的独立仿真/优化使用原桌面队列入口，不从助手模式推断权限。
3. 每次请求恢复、手动批准、自动倒计时、授权与最终入队均重新核对来源。操作模式 pending 或 approved 后切讨论时，回执转为可见的 `pending`，`release_policy=blocked`、`release_at=null`，保留输入、估算、拒绝原因 `release_error` 和 `requires_new_request=true`。不会悄悄删除记录，也不会留下可继续执行的旧批准。
4. 切回操作模式不能恢复旧代际的倒计时或批准；用户须在操作模式重新明确执行，产生新的真实请求/估算。旧回执仍可保留待定或由用户关闭；它不是一项可重试的自动授权。
5. 桌面提示刷新既有待决项时覆盖旧倒计时，显示阻断原因及“保留待定记录 / 关闭本次请求”。本地 UI 也阻止已知 blocked 请求的定时/确认回调；最终权限仍由持久服务决定，不能依赖 UI 缓存。
6. 已经 `submitted` 的队列任务继续按既有输入运行，不因切讨论自动取消、重启或修改。查询其状态、结果和已有持久资产不需要新计算。讨论助手不得以完成事件或结果读取触发后续导出；这由运行时只读工具/参数门禁另行约束。用户独立 GUI 的查看、取消、导出行为保持其原有权限。

## 异步与最终入队边界

`SchedulerStore.submit` 仅对关联 `estimate_id` 的新计算执行最终放行校验，且要求当前回执仍为 `approved`、来源匹配、UI 模式/代际有效。稳定任务身份的既有入队重试返回原任务，不重复创建任务。

最终入队与 UI 模式变更采用固定锁序：

1. 助手 authority 数据库执行 `BEGIN IMMEDIATE`，持有真实写保留锁；不是普通读事务，因此 WAL 模式下也能阻止 UI 模式写入穿越入队边界。
2. 在该短事务内取得 queue 数据库写事务，再核对当前回执及同一 authority 连接看到的 UI 模式/代际。
3. 提交 queue 事务后释放 authority 事务。UI 模式写只访问 authority 数据库，不反向取得 queue 写锁。

先赢得 authority 锁的入队属于模式变更前的既有任务，之后切模式不会自动取消它。模式变更先提交时，后续入队被拒绝并保留 blocked 回执。单纯在估算或冻结输入前后各检查一次，不能代替此最终边界。

## 定向离线验证

`tests/test_discussion_compute_policy.py` 使用临时 SQLite、冻结的本地 probe manifest 与直接 `SchedulerStore` 调用；不启动调度 daemon、worker、真实计算、provider 或网络。

覆盖所有旧短任务类型/60 秒边界、操作 pending/approved 切讨论、切回操作不恢复、历史缺可信 UI 记录、模型进度元数据不能授权、UI 模式覆盖不能扩权、跨会话回执、manual GUI 不误封、既有运行任务不取消、最终入队重检，以及 WAL 下用事件精确协调的并发模式切换。并发测试通过零超时写锁探针验证锁的实际存在，不依靠 sleep 竞争。

桌面队列快照还绑定 UI 自有的模式 epoch。模式实际改变时立即撤销旧本地倒计时；异步返回的旧 epoch 快照在更新事件游标之前丢弃。快速切回操作也不会重新接受旧倒计时。模式改变后的服务端回执刷新若失败，保留刷新需求，由后续正常轮询重试，不能把未刷新的缓存重新标为当前权限。相同模式的配置刷新不撤销有效的当前请求；独立外部请求保持原有确认行为。
