# Headless project persistence and dependency contract

Date: 2026-10-15. This foundation is independent of Qt, the launcher, and AI routing. It does not start calculations or introduce an optical/deposition algorithm.

## Ownership and public boundary

`ProjectStore` in `coat_sim/core/project_store.py` is the sole owner of the selected `.coatproj` descriptor, committed document membership, the designated deposition configuration, and recovery records. `ProjectStore.create(root, name, *, summary=None, notes=None)` creates a new project directory with the default `project.coatproj` descriptor and the existing project layout. `ProjectStore.open(project_file)` requires the exact selected descriptor file; its parent directory is the project root. Any filename prefix is allowed as long as the suffix is `.coatproj`. Each opened store captures that actual descriptor path: saves, stale-manifest checks, and reopen operations continue to use it rather than deriving `project.coatproj` from the directory. A directory, `project.json`, and a `.cproject` archive are never auto-open aliases. Every instance has its own project root and detached values; copied directories retain their persisted project ID, so the future session coordinator must require explicit reidentification before independent simultaneous writable sessions; there is no active-project singleton. `coat_sim/core/project_dependencies.py` owns bounded typed document parsing and dependency discovery. `coat_sim/project_cli.py` exposes the same services without GUI initialization.

Public calls: `ProjectStore.create(root, name, *, summary=None, notes=None)`, `update_information(information, *, expected_revision=None) -> {id, name, summary, notes, revision}`, `create_document(kind, document, materials=None) -> document_id`, `ProjectStore.open(project_file)`, `import_document(path, materials=None) -> document_id`, `add_deposition_configuration(name, process_document_id, parameters=None) -> configuration_id`, `save_document(id, document, materials=None)`, `set_default_configuration(id_or_none)`, `resolve_default() -> graph_or_none`, `resolve_document(id) -> graph`, `export_document(id, destination)`, `record_recovery(document_ids)` and `recover_session()`. `store.root` returns the resource directory and `store.project_file` the actual selected descriptor path. Managed in-memory films/expression templates and atomic material transfer follow [the template/document contract](project-template-contract.md). CLI `create-document` accepts their explicit JSON payloads; `save --materials` transfers new required resources in the same save. The read-only `manifest` property returns a detached dictionary; `maintenance_warnings` returns detached nonfatal cleanup warnings and CLI results include them when present. Import/material transfer is explicit; no catalog discovery or implicit global mutation occurs.

## Persisted format and dependency truth

An empty project is valid. The selected `.coatproj` descriptor is strict UTF-8 JSON kind `coat_sim.project`, version 1, with a UUID project ID, name, monotonic revision, document records, and optional `default_configuration_id`. The seven existing required fields remain, with optional project `summary` and `notes` text fields (each at most 20,000 characters). Existing version-1 descriptor content and retained object paths remain accepted without a read-time rewrite. This is an extension to version-1 path/metadata semantics: older strict readers reject named paths or additional metadata rather than interpreting a different graph. The explicit managed kind registry now additionally recognizes saved ray/appearance input envelopes and binary-input metadata; older readers reject an unknown kind clearly. The default descriptor basename is `project.coatproj`, but a selected descriptor may use any prefix, for example `/path/to/project/My-study.coatproj`. Open only that explicit `.coatproj` file; do not scan a directory, infer a path, migrate a legacy package, or open `project.json` or `.cproject` as a project descriptor. A suffix or non-regular-file mismatch is `invalid_project_file`; a symbolic link or reparse point in the path is `unsafe_path`. Each record contains its UUID internal ID, kind, project-relative path, SHA-256 of persisted bytes, and internal dependency IDs. Newly saved paths are portable, NFKC/casefold-unique, beneath `data/<typed-category>/r<project-revision>/<resource-name>.<extension>`; for example `data/sources/r00000001/Copper.csrc`. Legacy `objects/<generation-id>/<UUID>.<extension>` records remain accepted and untouched when read. Neither form can escape through `..`, absolute/drive paths, symlinks or reparse points. Typed file references within managed JSON are stable `UUID.<extension>` logical handles, resolved through the manifest by ID and kind, not relative filesystem lookups against the human-readable storage directory. The referenced IDs and manifest dependency list must agree. Missing/type-conflicting/hash-mismatched documents fail visibly; no global resource fallback is attempted.

Existing-project CLI and management operations take the selected descriptor path, not its directory. For example:

```sh
python -m coat_sim.project_cli inspect /path/to/project/My-study.coatproj
python -m coat_sim.project_cli resolve /path/to/project/My-study.coatproj
```

The separate `create` command still takes a new directory and creates its default `project.coatproj` there. For external project management/MCP operations, the existing request field named `root` likewise carries the explicit `.coatproj` file; only `create` uses `root` as a new directory. Responses retain `root` as the resource directory and also return `project_file` as the actual descriptor path. Internal SessionHost/root-lock routing remains keyed by the project directory identity. `ProjectOwnerLease.acquire(actual_project_file, project_id)` derives the same root/project-ID lock keys.

Descriptor and external package suffix recognition is case-insensitive (`.COATPROJ` and `.CPROJECT` are accepted); the selected descriptor's original filename and case are retained for subsequent writes. ZIP member names remain exact and case-sensitive, including the canonical `project.coatproj` entry.

A project-local deposition configuration (`coat_sim.deposition_configuration`, version 1) names one process document ID and stores the existing recipe calculation parameters, excluding path input. Numeric fields retain the existing settings/recipe units and semantics (geometry mm, rates nm/s, thickness nm, timing s, rotation rpm; source/monitor slots one-based and mask slots zero-based), without rounding or recalculation. Its configuration ID, when designated in the manifest, is the sole root for normal project opening. `open` validates the manifest and resolves its complete root closure afresh. Other project designs/configurations remain members without becoming the root or computing automatically. Clearing the root restores a valid unconfigured project without removing its member designs. Last-session/recovery information never substitutes for this root.

The headless activation boundary is `coat_sim.core.project_default_loading.load_project_default(store) -> ProjectDefaultPlan`. It calls only the selected-root resolver and returns `state` as `empty_project` (no managed documents), `no_default` (documents but no designated configuration), or `ready`. The ready plan carries the project ID/revision, selected configuration ID, process document ID, and detached copies of the existing resolved graph (`configuration`, `runtime`, `input_snapshot`, and typed document closure). Missing, corrupt, stale, or type-conflicting selected dependencies raise `ProjectError`; callers must show the failure rather than opening another configuration. The plan performs no calculation, GUI construction, global-catalog lookup, or recovery read. A process's existing `film_design_snapshot` is exposed, if present, as frozen provenance with its embedded optical materials. It is not a live managed `.cfilm` link; unrelated saved films are never guessed from names or matching design IDs. No new persisted schema is introduced.

External `.cproc`, `.cmac`, `.csub`, `.csrc`, `.cmsk` and `.cfilm` documents are copied into the project together with their complete supported dependency closure. Process machine/substrate references and machine source/mask references are rewritten to stable handles of the copied project documents. No source files or unrelated directory trees are included. Repeated references to the same external file share one copied document; basename collisions cannot merge content. Original schemas/normalization remain authoritative.

Existing process v7 `film_design_snapshot` and `film_design_import` are validated and preserved as embedded value snapshots. They do not claim a live `.cfilm` linkage. The complete-process-film producer now captures the full typed film material closure, including unused expression symbols and optimization candidates, from its supplied service provider. Existing schema-version-1 snapshots that lack such unused records retain their numerical/process validity; editable project-draft restoration requires the full embedded closure and fails with the missing material/optical-set pair rather than guessing current project/global records or removing workflow metadata. Re-export the complete original film with its original referenced records to recover editable provenance; see [the film import compatibility boundary](film-process-import.md#ui-state-and-failure-boundary). Source material and substrate optical material snapshots are already inline and are preserved by existing validators. Standalone `.cfilm` documents use material/optical-set IDs, not material file paths. Material dependencies enumerate substrate, both face layers, material media, every `expression.symbols` layer-shaped value, and the typed version-1 `workflow_settings.optimization.structure_materials` candidate reference list. Malformed/unsupported candidate-reference configurations fail rather than guessing from arbitrary JSON strings. Other workflow fields remain opaque editor settings; future typed resource fields require an explicit adapter update. Their referenced records must be supplied explicitly in `materials` or already exist in this project; records are copied as project-local `coat_sim.project_optical_material` version-1 resources with validated optical sets. Film resources represent the existing frozen-film optical record shape, not arbitrary global material packages; no unsupported automatic process-to-film inference is introduced. Equal material IDs with different content are a conflict; they are never silently replaced. `workflow_settings.simulation/optimization` survives film import/export unchanged.

## Atomicity, errors and recovery

`save_document` saves an editor working document with its existing internal ID; all typed references remain bound to the same stable UUID handles across renamed files and category revisions. Ordinary opening therefore reads current saved versions, while previously admitted jobs continue to use their own frozen snapshots. Saving does not read external references: import a new dependency first and then bind its stable UUID filename. No operation calls `os.chdir` or changes a global data root.

Mutations stage new immutable files in a private fresh `objects/<transaction-id>/` directory, validate the resulting graph, exclusively publish each typed `data/<category>/r<revision>/` directory, then atomically replace the captured `project_file` descriptor as the sole commit point. The private stage is removed on normal success/failure. No current resource bytes are overwritten; a name change writes a new human-readable basename in a new revision while retaining its UUID and every earlier referenced file. Existing category revision names, including case variants and interrupted leftovers, get a numeric `-2`, `-3`, ... revision-directory suffix rather than being merged or replaced. A concurrent target appearing after preparation fails closed and its contents are never cleaned as this transaction's files. Managed input JSON/configurations/optical records and explicitly declared binary input dependencies participate. Unreferenced result files, run data and arbitrary external files are not copied. A configuration-referenced deposition `.coatasset` follows its typed input closure; see [simulation input/asset safety](project-simulation-input-contract.md). Unchanged input bytes use same-filesystem hard links when supported, with a normal byte-copy fallback. Every mutation still validates/serializes O(total managed input bytes); historical generations remain retained and cleanup/compaction is pending. Files are bounded by the existing 32-MiB JSON limit, with a project safety ceiling of 1000 managed documents/256 MiB of input JSON; these are resource limits, not scientific precision claims. Existing referenced bytes are never overwritten; a failed publication preserves the previous descriptor and cleans only its own staged/published directories and new binary assets. A crash before descriptor publication may leave unreferenced named revision directories; opening still reads the old complete manifest. A later save chooses a new directory, and automatic deletion/compaction remains pending. A writer lock excludes concurrent writers; a store checks its captured descriptor fingerprint before each mutation and rejects stale state rather than losing changes. The lock records project ID/revision, PID, a per-write identity and UTC creation time for inspection. A crashed writer may leave unreferenced staged files or a lock: the foundation reports the lock and does not break it automatically. A PID alone cannot establish that an owner is alive or that the lock is stale; supervised/manual lock recovery is pending. The lock is removed after normal success/failure. If cleanup fails after publication, the save remains successful and the store already reflects the committed revision; a maintenance warning reports the retained lock rather than presenting the committed save as rolled back. On an earlier write failure, cleanup warnings do not hide the original error. Cross-process concurrent readers must reopen to observe the new descriptor revision.

Export writes a new explicit destination directory containing only the selected document closure and its project-local resources, with references rebased, and publishes the directory only after completion; existing destinations, including concurrently created empty directories, are rejected by an exclusive rename primitive. Linux uses `renameat2(RENAME_NOREPLACE)`, macOS uses `renamex_np(RENAME_EXCL)`, and Windows uses its no-replace `os.rename` semantics; unsupported hosts/filesystems fail closed. This cloud verifies the Linux route; native Windows/macOS runtime checks remain pending. See [Linux rename semantics](https://man7.org/linux/man-pages/man2/rename.2.html), [Apple exclusive-rename flag and signature](https://raw.githubusercontent.com/apple-oss-distributions/xnu/main/bsd/sys/stdio.h), and [Python os.rename](https://docs.python.org/3.12/library/os.html#os.rename). It never writes the global catalog. Exported process/geometry documents are directly readable by the existing standalone services. Exported film material envelopes are supplied explicitly as the `materials` mapping when reimporting a film. `export.json` and exported `.cdep` configurations are not yet accepted as a package import: package-level identity-preserving reimport is pending; importing the process file and creating a configuration is supported. Recovery records are separately written strict JSON containing project ID, revision and existing internal document IDs. `recover_session()` is an explicit abnormal-recovery read, and rejects a changed revision/project identity; normal `open` never reads it. Recovery currently records saved document IDs and returns their saved graphs; it does not persist or restore unsaved editor draft bytes. Draft recovery belongs to the future session adapter and is pending. Existing `FilmMaterialLibrary` reads its own `data/materials` layout; resolved graphs expose detached `materials` records, but the GUI/film-service project adapter is pending and validation alone is not claimed as desktop simulation integration. No background/asynchronous work is owned here; callers can cancel before entering a mutating call, and publication itself is a synchronous non-cancellable transaction.

## Acceptance

Tests cover empty/multiple project isolation, designated-root selection, fresh complete dependency closure without original files, same-basename imports, unsupported/missing/type-conflicting dependencies, finite strict JSON, portable path and link boundaries, explicit film material closure and conflicts, inline snapshots and film workflow preservation, publication rollback, stale-writer detection, explicit export, recovery-only behavior and headless CLI smoke tests. UI attachment, dirty editor sessions/draft recovery, package reimport, generation compaction and execution routing are separate follow-on adapters.

## Measured generation cost

A local CPython 3.12/Linux cloud check on 2026-10-14 used 68 managed input documents (one process, one machine, one substrate, 64 distinct sources and one configuration). Saving one source took 46.350 ms for 17,857 total JSON bytes, and 85.647 ms for 1,297,857 bytes with synthetic 20,000-character source notes. In both cases 67 unchanged documents shared their previous inode via hard links. These are one-shot local measurements, not a latency guarantee or a Windows/storage benchmark. Serialization/validation still scales with all managed input data; unsupported hard-link hosts copy those bytes and retained generations consume more disk space. No result assets were included in this check.

## Human-readable resource naming and project information

`core/project_paths.py` is the typed category registry. Sources, substrates, masks,
machines, processes, films, expression templates, materials, configurations,
raytrace, appearance and small binary-input metadata live in their corresponding
`data/` categories. Binary payload capabilities retain the existing separately
validated `assets/<generation>/<UUID>.<role suffix>` format; this change does not
rename large owned bytes, run data or results. Stable chooser handles use
`data/<category>/UUID.<extension>` and do not themselves create files. Explicit
standalone closure export still uses flat UUID filenames, so its typed relative
references remain directly readable by standalone services.

A resource basename comes only from its validated display name (or the existing
unnamed-type placeholder). NFKC normalization, forbidden/control-character
replacement, trailing-dot/space stripping and Windows device-name protection
produce one portable basename. Names are bounded to 80 characters and 180 UTF-8
bytes before suffix/extension; the stored display name is never shortened or
changed by this filesystem conversion. Case/Unicode-equivalent, sanitization and
truncation collisions within a category use ` (2)`, ` (3)`, ... in persisted
manifest order. Suffix allocation starts fresh in each revision, so an ordinary
edit does not continually add suffixes. Names do not provide path components.
The existing physical basename may be used when saving an explicit binding only
if it is globally unambiguous; the save canonicalizes it to a UUID handle. A
missing/ambiguous filename is rejected rather than guessed.

`update_information` accepts only `name`, `summary`, `notes`; name is trimmed,
nonblank and at most 100 characters, while summary and notes are independent
text up to 20,000 characters. Omitted fields retain their previous presence or
absence. Its detached return always projects missing optional fields as empty
strings. The optional optimistic token is the integer project revision; a
stale token or descriptor raises `stale_project`. A real metadata change writes
only the captured `.coatproj` descriptor under the ordinary writer lock and
increments the project revision; it does not move/copy documents, change the
project ID/default, or create a resource generation. A no-op leaves the
descriptor bytes unchanged. Runtime/launcher callers must retain their existing
owner/lease routing; a descriptor lock is not a substitute for session ownership.

This is a storage protocol, not a physical algorithm. Numeric JSON values,
coordinate systems (geometry mm), film thickness/wavelength nm, and existing
source/process units remain exact as before; no resampling, rounding or
convergence/accuracy claim is introduced. Naming, revisions and collision rules
are project conventions, with no external scientific validation claimed.
Tests in `tests/test_project_named_resources.py` cover path safety, rename
identity, read-only legacy opening, current/old bytes, dependency closure, package
and recovery parity, descriptor failures, destination races and metadata I/O.
