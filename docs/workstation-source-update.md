# 发布工作站源码更新与实际版本验收

发布后应维护实际运行副本的版本同步。每次报告分别列出 GitHub `main`、CNB `main`、运行副本实际 `HEAD` 和 `coat_sim/version.txt`；某端未完成时写明阻塞，不能只报告远端镜像。远端同步方法见 [CNB 镜像同步](cnb-mirror-sync.md)。

本流程不提供无条件 reset/clean 更新器。它要求先审查差异和可恢复记录，再对明确的受跟踪源码范围执行可回滚事务；工程、材料与运行环境保留原处。不要提交机器私有路径、用户名、凭据或具体任务记录。

## 1. 明确目标和只读状态

1. 读取当前 AGENTS 和适用技能要求，记录明确完整目标 SHA、版本、当前分支、index/staging 状态和活跃进程。GitHub 访问始终命令级使用 `http://127.0.0.1:10808`，失败不回退直连。
2. 在独立临时 checkout 中取得并核验目标。准备期间不更改运行副本，不执行其未提交脚本，不把当前目录当成已授权可覆盖的完整部署单元。
3. 用任务临时目录内的**独立新索引**读取 BASE 与目标，对全部受跟踪路径做比较。新索引由 `read-tree` 构建，使用单独的 `GIT_INDEX_FILE`；不替换真实索引。禁用 fsmonitor、可选索引写入和隐式 lazy fetch，隔离继承的 Git 上下文。
4. 不依赖普通 `git status` 的旧 stat 缓存。旧索引可能隐藏已有的换行差异；新索引比较与原字节哈希应相互印证。比较前后对全部 BASE/目标受跟踪路径计算原字节哈希，确保检查期间内容稳定。

## 2. 逐项分类，保护最新基线

分别识别：已被上游包含的改动、仅换行差异、独有功能、过期源码、本地删除、未跟踪/忽略的用户文件，以及目标新增路径与现有文件的碰撞。任何未知语义变化或新用户编辑都应停下复核，不能把“新索引发现”自动当成覆盖授权。

只在当前目标源码中重新实现仍有必要的独有功能。禁止将旧分支 merge/cherry-pick 到新版、整文件覆盖新版，或批量恢复旧代码、删除项、未跟踪目录和历史诊断豁免。若上游已包含某功能，不再恢复旧实现。

静态检查基线的诊断列表和移除记录必须保留当前目标语义。若审查后的工具修改需要更新 `config_digest`，只由当前输入字节重新派生该字段，并证明其他基线数据未变。

## 3. 最小可恢复保存

- 保存即将被替换的独有源码/文档原字节、需要保留的未跟踪用户文件、tracked binary diff、HEAD/index 状态、删除列表与哈希清单。
- 新发现的已审查格式差异也要保存原字节并绑定哈希。恢复副本必须验证，不能只记录“已复制”。可在临时独立 BASE 索引中应用差异，验证能重建原 tracked 字节及删除状态。
- 工程、材料、私有 Python 环境及用户数据保持原处。不要默认复制整个仓库、`.git`、运行环境、产物或缓存；不要自动删除部分恢复材料。
- 恢复文件和日志属于本机私有运行资料，应放在明确的非提交目录，不上传、不入仓。不要记录凭据或读取私钥。

## 4. 制定并验收精确计划

在干净的当前目标 checkout 上准备经过审查的独有改动。记录完整目标、候选文件哈希、允许的原源码哈希、精确写入/删除集合和保护目录。对所有非独有修改的候选字节，证明它们等于目标提交。

独立新目标索引必须覆盖全部受跟踪路径，证明计划包含全部待解决差异，预计最终差异仅为明确审查过的集合。路径不得越出根目录或经过意外 reparse point；拒绝工程、材料、环境、缓存路径碰撞。无删除计划不能被实现成目录清理。范围变化必须先审查并与当前授权核对。

使用已存在、可信的运行环境，仅对已验证的新源码和审查过的独有改动执行必要的定向验证。不要安装或运行未知下载内容，不以旧工作区测试结果替代新候选验收。

## 5. 执行时再次检查，保留安全恢复

实际写入必须显式请求，默认只检查。在拥有唯一自建 index lock 的短事务中重新运行完整新索引预检，比较所有原字节哈希与已审查计划；每个文件替换前再次检查它的原字节。真实 index 变化、分支变化、碰撞或未知用户编辑均停止，不能抹掉并发工作。

检查活跃工程/计算进程时包含品牌化桌面宿主，而不只检查 `python.exe`。需要关闭或可能存在未保存工作时先报告；不强制终止用户进程。保持原目录与启动入口路径，避免目录整体交换影响材料和环境。

只导入已核验的本地提交对象，只替换计划中的源码。使用保留 ACL 的逐文件原子替换、独立构造的新 index 和带旧值校验的本地 ref 更新，记录进度。该事务不创建本地提交、不改仓库权限、不改全局 Git/系统网络、不向远端发布独有改动。

失败时逐项尝试安全恢复；日志或某个 ref 恢复失败不能阻止其他独立恢复。只有文件/index/ref 仍属于本事务时才恢复；被其他进程改动的状态保留并报告。新生成文件保留在恢复区，不能当成用户数据永久删除。进程被中断时可能需要人工使用 BASE、已验证差异和原字节恢复，不能宣称未测试的崩溃恢复保证。

可恢复的检查问题应先定位、修正计划并复核，再依当前授权继续；不能盲目循环重试。官方审批拒绝须记录动作、目标、原因和是否执行，不绕过。只有新的相关授权解决拒绝且确认之前未执行时，才按规定尝试；结果不确定先核查。

## 6. 实际运行副本验收

完成必须以原运行目录为准：

1. 核对实际 `HEAD`、分支、权威 `coat_sim/version.txt`、空 staging、精确最终差异、未跟踪用户文件及保护文件哈希。
2. 再次使用独立**新目标索引**检查全部受跟踪路径，避免旧 stat 缓存掩盖差异。证明旧源码和旧诊断豁免没有重新注入。
3. 用保留下来的可信解释器检查实际源码关键导入，核对模块加载位置。运行 `tools/app_version.py check --previous-version <先前版本>`，验证真实版本文件。
4. 核对启动入口与目标源码一致，可编译并以非 `__main__` 名称安全加载入口，检查其根目录和版本引用；不调用 GUI 主入口。读取真实版本格式化路径，不能用人为注入预期版本替代验收。Git HEAD 单独核对，不能把外部提供的 SHA 冒充程序自动检测结果。
5. 执行必要的定向回归，关闭 bytecode 写入，把测试临时目录限制在任务区。之后再次验证工程、材料和环境保护记录。
6. 分别报告源码解析、安全入口加载、完整 GUI 启动和已安装安装器验收的实际范围。没有执行的项目不能标记完成。

报告应保留最小恢复位置、公开可分享的摘要及本机私有证据，并分别说明三端 SHA/版本。后续发布重复这一闭环，不把远端成功当成本机已更新。
