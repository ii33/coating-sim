## 同条件与计时范围

## 实测热点与改变

完整cProfile与低干扰计时分开。原profile总自身216.67秒，最终64.16秒；这是探针下的诊断，不能当作另一组速度基准。自身时间分类不重叠，累计时间嵌套且有心跳线程等待项，不能相加为CPU占比。

| profile自身类别 | 原 / 秒（占比） | 最终 / 秒（占比） |
|---|---:|---:|
| n/k采样与验证 | 49.56（22.87%） | 0.98（1.53%） |
| 深拷贝 | 45.69（21.09%） | 15.46（24.09%） |
| 光学/Jacobian及其准备 | 41.52（19.16%） | 12.88（20.08%） |
| JSON编码 | 16.89（7.80%） | 0.49（0.77%） |

具体原调用：prepare_optical_set 11090次累计31.35秒，index_series累计70.86秒，_checked_frozen_snapshot约1491次累计27.17秒，_checked_material_rows3698次累计12.31秒。档案及完成候选内部深拷贝也是实际热点。四个不同角度/偏振均有物理意义，不把四次条件调用称作无效重复。

`_analytic_one_polarization`自身32.31秒/3698次，改为双向链后6.15秒/3791次。旧方式在每层传播全部变量[W,V]矩阵，约O(WLV)；新方式保存局部复数2×2链式系数，再由入射端组合各层厚度导数，O(WL+WV)，仍完整返回R和T的解析Jacobian。原coherent_rta功率值、被动q、通量、临界点/奇异点拒绝与变量列序不变。

生产训练和每次独立审计各自持有深复制验真的私有准备态。只复用sampler及精确网格、材料、use_k和外推策略对应的只读n/k；64项/32 MiB LRU是内存策略，不是搜索或波长上限。普通公共调用仍验真，不能信任任意可变dict的SHA。候选、score和审计结论不进入光学缓存，缓存命中仍按原边界计数和取消。

内部档案仅共享通过精确类型/标量检查的冻结FilmConditionError tuple，所有可变design/response/Jacobian及外部observer/checkpoint/result边界继续独立复制。异常或自定义可变字段回原deepcopy，未修改全类复制行为。

原profile里SLSQP原生核229次自身0.514秒，L-BFGS-B原生setulb1160次0.017秒；SLSQP包装器累计37.60秒主要包含回调，不等于线性代数自身时间。checkpoint实际原子写两次累计0.187秒、typed JSON snapshot十次累计约1秒，不能把本例主要瓶颈归咎于磁盘。此顺序minimax不能仅靠增加候选worker数按比例提速；本例请求1 worker，不将其作为19进程实用覆盖证据。

## 2026-10-22 CI 诊断顺序与清理收尾

`d36b204` 的 algorithm 与 quick 作业均有同一组 10 项原审计断言失败。原因是提前构造准备态时先报摘要不匹配，遮蔽了缺失材料、光学集及 k 来源有效域的上下文诊断。现先严格检查来源，再惰性创建一次独立准备态；来源有效但摘要损坏仍在任何 TMM 前拒绝，不自动重签摘要。请求与候选在观察者回调前独立复制，使严格来源采样、准备态和最终元数据对应同一输入。单次审计材料复用仍保留。

相关回归 **361 项通过**（含全部原审计 36 项和新增 35 项），本轮 3 个 Python 文件的 Ruff/mypy 诊断均为 0，未改基线。独立 Sol6.1 只读审查接受审计修补。原冻结请求、材料、目标、1 nm 训练、300 秒/4000 次预算、全部独立审计与取消边界均保持。正式服务入口新进程单次检查 **29.204 秒**、CPU **28.609 秒**，审计 minR **0.9873549455679516**，32 层、总厚 **2569.6454496228444 nm**；754 次逻辑评价、2 次审计准入、773 次审计物理调用、48775 审计波长点，与修补前受控运行一致。仅在子进程临时设单数学线程；此次耗时处于上表既有波动范围，单次检查不宣称统计等价或新增提速。

另一个独立问题是 Linux contract 在 `test_manual_calculation_reads_latest_unsaved_same_owner_on_every_start` 已通过后，于 paired fixture 的全局 DeferredDelete 清理发生 SIGSEGV（退出 139）。本机尚未复现该崩溃，但确认前序 layer-dropdown 测试只排队删除，未完成其 QML window/component/engine 原生销毁。补丁在该测试自己的清理边界逐个完成接收者定向删除，并断言销毁顺序、原生对象失效及不消费无关待删除对象；未改生产 GUI 或删除原全局清理。Windows 相邻测试带 CI 诊断插件 **13 项通过**，包括原设计交互/颜色断言。该隔离缺口真实存在，**是否消除 Linux SIGSEGV 仍待新 CI，不能称已证实崩溃根因或全套通过**。
